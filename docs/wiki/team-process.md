# Процесс команды CampusFix

## Рабочая модель

Для проекта используется гибридный подход.

Ключевые вехи и обязательные артефакты курса фиксируются заранее, а разработка продукта ведётся итеративно.

## Работа с задачами

Основные статусы на GitHub Projects:

Backlog → Ready → In progress → Review → Blocked → Done

## Правила работы с задачами

- каждая задача должна иметь владельца;
- задача должна иметь Size;
- задачи из Backlog переходят в Ready после уточнения требований;
- задача считается завершённой только после проверки;
- заблокированные задачи переводятся в Blocked;
- причины блокировки должны быть зафиксированы.

## Ветки

Используются отдельные ветки под каждую задачу.

Формат:

feat/CF-XX-short-name  
fix/CF-XX-short-name  
docs/CF-XX-short-name  
test/CF-XX-short-name

Примеры:

feat/CF-12-create-ticket  
docs/CF-05-update-wbs  
fix/CF-21-ticket-status

## Коммиты

Используются короткие понятные префиксы:

feat: новая функциональность  
fix: исправление ошибки  
docs: документация  
test: тесты  
chore: служебные изменения

## Pull Request

Прямой push в main после первоначальной настройки не используется.

Рабочая схема:

ветка → commit → push → Pull Request → review → merge в main

## Правило ветки

Одна ветка соответствует одной задаче.

Желательная длительность жизни ветки — не более 3 дней.
